## Why it changed nothing (diagnosed after the verdict)

Both arms explored exactly the same nodes, so the switch was checked first. It
is reached: `reconstruct` calls the module's `search`. The failures on the
holdout's `multi_hop_3` are the wrong-axle pattern, but the mechanism is not
the one registered. Case `multi_hop_3-101`:

- returned `h1` (bay 16 → genset-4), `c0067` ("standard axle set run 4.2 bar"),
  `f0003` ("the genset-4 oil-temperature trip **is set** at 104 °C");
- needed `h1`, `h2` (genset-4 re-fitted with the heavy axle set), `h3`
  ("heavy axle set run 3.6 bar").

The wrong chain is "connected" only through **set**, a word every axle rule
shares and that also occurs as a verb in an unrelated memory. Both the right
and the wrong chain survive the beam, and goal selection prefers the one with
the lower retrieval cost. Reordering expansion cannot change that, which is
why the registered change had no effect.

This diagnosis was made **on the holdout**, after its verdict was recorded. So
the holdout is spent for any change built on it. The follow-up, P1c, is
registered against a second fresh holdout.

The change is **kept off** (`chains.DISCRIMINATING_COVER = False`), as the
registration required.
